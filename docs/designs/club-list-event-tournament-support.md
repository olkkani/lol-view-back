## Problem Statement

`GET /clubs` today returns all currently-active `club_profiles` as a flat, single-purpose list, with no concept of "kind." The domain model assumes every club is a standing pro team (`is_active`, `founded_date`/`disbanded_date`, and long-term `user_followed_clubs` follow semantics all bake this in). Event-style competitions (Asian Games, national-team exhibitions, other one-off tournaments) have participants — e.g. national teams — that don't fit that assumption, but `match_participants.club_id` forces them to exist as `clubs` rows regardless, for match data referential integrity. The open question was never "can event participants exist in the DB" (they must) — it's whether `GET /clubs`'s default response should mix them in with standing pro teams or keep them out.

## Status Quo

No workaround exists inside the product today — event-style competitions aren't seeded at all (current league seed data is 100% standing pro leagues: Worlds, MSI, LCK, First Stand, Esports World Cup, KeSPA Cup). The founder's real-world status quo during the Asian Games was falling back to other sites/portals entirely.

## Constraints

- `match_participants.club_id` is the only column representing "who played" — event participants must be `clubs` rows regardless of any list-display decision. This isn't optional.
- `is_active`, `founded_date`/`disbanded_date`, and `user_followed_clubs` (long-term follow) are all standing-team-shaped. An event participant (e.g. a 2026 Asian Games national roster) doesn't have a meaningful founded/disbanded date and arguably shouldn't be "followable" the same way.
- No `GET /leagues` or `GET /tournaments` list endpoint exists yet — only `GET /matches?range=`, `GET /clubs`, `GET /matches/{id}/head-to-head`, and bracket/auth endpoints. Any event-discovery surface beyond the club list would be new work, not reuse.

## Approaches Considered

### Approach A: Mixed list + `club_kind` tag
Add `club_kind` (STANDING/EVENT) to `clubs`, default STANDING via backfill. Event clubs appear in the same `GET /clubs` list, tagged.
- Pros: ships in hours; solves the founder's own pain directly this week.
- Cons: stretches standing-team semantics (`is_active`, founded/disbanded, indefinite follow) over entities that don't fit them; every future event permanently bloats the default list with no archive/hide logic.
- Rejected — corrupts the follow-list's meaning for a stopgap fix.

### Approach B: Standing-only list, event clubs surfaced elsewhere
No schema change. `GET /clubs` stays exactly as-is (standing-only). Event clubs exist in the DB but are only reachable via tournament/match views.
- Pros: zero risk to what already works; matches how event rosters are treated everywhere else (not "followable" entities).
- Cons: doesn't fix the founder's pain this week — no tournament/league list endpoint exists yet to serve as that alternate surface. Punts to work that doesn't exist.
- Rejected — solves nothing today given no alternate discovery surface exists.

### Approach C: `club_kind` filter, default-excluded (chosen)
Same schema addition as A (`club_kind` column, STANDING default via backfill), but `GET /clubs` defaults to `club_kind=STANDING` unless a caller explicitly requests `?kind=EVENT` or `?kind=ALL`.
- Pros: one source of truth, no new migration needed for the next event type; default follow list stays semantically clean; opt-in path exists for a future tournament/event page to call explicitly.
- Cons: more work than A/B this week (query param handling, jOOQ changes, follow-eligibility decision for EVENT clubs); the `?kind=EVENT` path has no caller yet without a tournament/event browse surface.

## Recommended Approach

Approach C, scoped narrowly: ship the `club_kind` column + `GET /clubs?kind=` filter now (default STANDING, unchanged behavior for existing callers). Defer building the actual caller (a tournament/event banner or page) until a `GET /tournaments`-style endpoint exists — that's the real fix for the founder's lived pain, and building it is separate, larger scope.

## Open Questions

- Should EVENT clubs be followable at all via `user_followed_clubs`, or should follow require `club_kind=STANDING`? Not resolved this session — deferred until an EVENT-club consumer exists.
- Should `club_kind` live on `clubs` (identity-level) or `club_profiles` (temporal, in case a club's "kind" could theoretically change)? Recommend `clubs` — kind is closer to permanent identity than name/logo/region, which do change (SCD-2 already handles those).

## Success Criteria

- `GET /clubs` (no query param) returns identical results to today — no regression for existing/future standing-team consumers.
- `GET /clubs?kind=EVENT` returns event participants (e.g. a seeded Asian Games national team) without requiring any change to `match_participants` or `club_profiles`.
- Next event-style tournament (not just Asian Games) can be seeded and queried without a second schema migration.

## Dependencies

- No `GET /tournaments` or `GET /leagues` list endpoint exists yet — the actual discovery fix for the founder's Asian Games experience depends on that separate, unscoped work.
