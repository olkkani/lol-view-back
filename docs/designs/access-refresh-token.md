## Problem Statement

현재 `JwtService`는 단일 JWT(만료 24h, refresh 없음, revocation 수단 없음) 방식이다. 이 구조는 소셜 로그인 설계 당시(design doc `jin-main-design-20260819-170141.md`) "side project 규모에서는 감수할 트레이드오프, 문제되면 그때 denylist 등을 검토"로 의도적으로 보류된 것이었다. 사용자가 실제로 두 가지 불편을 겪었다: (1) 만료가 짧아 사용 중 자주 재로그인해야 함, (2) 유출/로그아웃 시 만료 전 즉시 무효화가 안 됨. 지금이 그 재검토 시점이다.

## What Makes This Cool

단일 토큰 구조의 "재로그인 빈도"와 "무효화 불가"는 서로 다른 축의 문제인데, 하나의 메커니즘(refresh token)으로 둘 다 해결된다는 게 이 설계의 핵심 통찰이다. Access token은 짧게 유지해 유출 시 피해 시간을 최소화하면서도, refresh token 덕분에 사용자는 재로그인 없이 세션을 유지한다.

## Constraints

- 프론트엔드는 웹, httpOnly 쿠키로 토큰 보관(사용 중/예정) — localStorage 기반이었다면 refresh token 보관 자체가 XSS 위험을 키워 이 설계가 성립하지 않았을 것.
- side project 규모 — 신규 인프라(Redis 등) 추가는 과함. 기존 RDB에 테이블 하나 추가하는 수준으로 해결.

## Premises

1. Access/refresh 분리 자체는 revocation을 자동으로 주지 않는다 — refresh token을 DB에 저장하고 rotation/폐기 체크를 해야 revocation을 얻는다. — **동의**
2. 짧은 재로그인 불편은 access token 만료만 늘려도 해결되지만, 그러면 유출 시 피해 시간이 늘어나는 트레이드오프가 생긴다. — **동의**
3. 사용자가 진짜 원하는 건 revocation이고, refresh token은 그걸 안전하게 구현하기 위한 수단이지 목적이 아니다. — **동의**

## Approaches Considered

### Approach A: Access(짧음) + Refresh Token, RDB 저장 + Rotation (선택됨)
Summary: Access token 15분~1h, refresh token 7~30일, 둘 다 httpOnly 쿠키. Refresh token은 `refresh_tokens` 테이블에 해시로 저장. `/auth/refresh` 호출 시 검증 후 새 access+refresh 재발급, 기존 refresh는 폐기(rotation)로 탈취 재사용 탐지.
- Effort: M
- Risk: Low-Med
- Pros: 업계 표준 패턴, revocation 가능(DB row 삭제), rotation으로 탈취 탐지 가능, 신규 인프라 없음(기존 RDB 재사용)
- Cons: 상태 저장 필요(만료 row 정리 배치), 동시 탭에서 refresh 경쟁 조건 처리 필요 — grace period로 완화(아래 Rotation 정책 참고)
- Reuses: 기존 `JwtService`, `JwtAuthenticationFilter`, `user_identities` 테이블 패턴

### Rotation 정책 (구현 필수 결정사항)

**Grace period.** 엄격한 1회용 rotation은 동시 탭(같은 사이트를 여러 탭에서 열어둔 상태)에서 흔히 오탐 로그아웃을 유발한다 — 탭 A가 먼저 refresh에 성공해 토큰을 교체하면, 탭 B가 곧이어 같은(이미 폐기된) refresh token으로 요청해 "탈취"로 오판된다. 폐기된 refresh token이라도 폐기 후 짧은 기간(예: 10~30초) 안에 재사용되면 정상 동시 요청으로 간주해 직전에 발급된 access+refresh를 그대로 반환한다. 이 기간을 넘긴 재사용만 탈취로 취급한다.

**탈취 탐지 시 대응.** grace period를 넘긴 폐기된 refresh token 재사용 발견 시: 해당 `user_id`의 `refresh_tokens` 전체 row를 `revoked_at`으로 무효화하고, 클라이언트에는 401과 함께 재로그인을 요구하는 응답을 반환한다. 이 대응 로직이 없으면 "탐지"만 하고 아무 조치도 없는 셈이 되어 Success Criteria의 탈취 대응 항목이 충족되지 않는다.

**해시 알고리즘.** `token_hash`는 SHA-256(빠른 해시)을 사용한다 — refresh 요청마다 조회를 위해 해시를 계산해야 하므로 bcrypt 등 의도적으로 느린 해시는 부적합하다. Refresh token 자체가 충분한 엔트로피(32바이트 이상 랜덤)를 가지므로 salt나 느린 KDF 없이도 안전하다.

### Approach B: 단일 JWT 유지 + Denylist만 추가
Summary: refresh token 도입 없이 로그아웃/무효화된 토큰의 jti만 별도 저장소에 기록해 검증 시 체크.
- Effort: S
- Risk: Low
- Pros: 변경 최소, 기존 design doc의 "문제되면 denylist 검토"와 일치
- **거부됨**: 재로그인 빈도 문제가 해결되지 않고(access 만료를 늘리면 유출 위험 증가), 사용자가 원한 access/refresh 학습 목적과도 안 맞음

### Approach C: Access+Refresh, Redis 저장
Summary: A와 동일하되 저장소를 Redis로 둬 TTL 자동 만료.
- Effort: M
- Risk: Med
- Pros: TTL 자동 정리, 조회 빠름. `libs.versions.toml`에 `spring-redis`/`embedded-redis` 의존성이 이미 정의돼 있어 신규 추가 부담이 예상보다 적을 수 있음(활성화 여부 미확인).
- **거부됨**: Redis 활성화 여부가 확인되지 않은 상태에서 인프라를 늘리는 선택은 side project 규모에서 과함. Redis가 실제로 이미 운영 중이라면 재검토 여지 있음.

## Recommended Approach

**Approach A** — 기존 RDB에 테이블만 추가하면 되어 신규 인프라 리스크가 없고, revocation과 rotation을 둘 다 학습하는 목적에도 부합한다.

## Open Questions

- Refresh token 저장 형식: opaque random string(권장, JWT로 만들 필요 없음) vs 별도 JWT — 다음 세션에서 확정.
- 만료된 refresh_tokens row 정리: 배치 스케줄러 vs DB 자체 TTL(`expiration_time` 컬럼 + 정기 삭제 쿼리).
- Access/refresh 만료 시간 구체값 (예: 30분/14일 등) — 사용성과 보안의 트레이드오프이므로 실사용 패턴 보고 조정.

## /plan-eng-review 반영사항 (2026-09-04)

**설정 스키마.** `application.yaml`의 `jwt.expiration-hours: 24`(단일값, :135)를 `jwt.access-expiration-minutes` + `jwt.refresh-expiration-days`로 분리한다. 단위를 명시적으로 나눠 소수점 혼동(예: 15분을 0.25시간으로 표기)을 방지한다. `JwtService` 생성자 시그니처도 함께 변경.

**엔드포인트 네이밍.** 기존 `AuthRestController`의 `GET /me`(:13)를 포함해 인증 관련 엔드포인트를 `/auth/*` prefix로 통일한다 — `/auth/me`, `POST /auth/refresh`, `POST /auth/logout`. `/me`를 사용하는 다른 호출자가 없는지 확인 후 이전.

**httpOnly 쿠키 구현.** 코드베이스에 쿠키 관련 코드가 전혀 없음을 확인했다(현재 `OAuth2SuccessHandler`는 JSON body로 토큰 반환, :48-50). Constraints에서 전제로 삼은 httpOnly 쿠키 보관을 이번 구현에서 실제로 만든다 — `Set-Cookie` 응답에 `HttpOnly`, `Secure`(HTTPS 전용), `SameSite=Strict` 또는 `Lax` 명시. **Path는 access token과 refresh token이 다르다**: access token은 `/auth` 밖의 모든 API(`anyRequest().authenticated()`로 보호되는 전 엔드포인트)에서 필요하므로 `Path=/`로 설정하고, refresh token은 `/auth/refresh`·`/auth/logout`에서만 쓰이므로 `Path=/auth`로 좁게 유지한다. (최초 구현에서 두 쿠키 모두 `Path=/auth`로 설정했다가 whole-branch 리뷰에서 access token이 `/auth` 밖 요청에 전송되지 않는 버그로 발견되어 수정됨.)

**RefreshTokenService 분리.** `JwtService`는 access token(서명 검증) 전담으로 유지하고, refresh token의 DB 조회/rotation/grace period 로직은 별도 `RefreshTokenService`로 분리한다. 성격이 다른 두 책임(서명 검증 vs DB 조회)을 한 클래스에 두지 않는다.

**동시 요청 레이스 방지.** Grace period 로직에서 동일 refresh token으로 동시 요청이 도착하면 둘 다 "아직 폐기 안 됨"으로 읽어 각자 새 토큰을 발급하는 레이스가 생길 수 있다. `refresh_tokens` row를 `SELECT ... FOR UPDATE`로 잠가 짧은 트랜잭션 안에서 배타적으로 처리한다.

**인덱스.** `refresh_tokens` 테이블에 `token_hash`(unique) + `user_id` 인덱스를 마이그레이션에 포함한다. `token_hash`는 rotate 조회의 핵심 경로, `user_id`는 탈취 탐지 시 "해당 유저 전체 무효화" 쿼리에 필요.

**테스트 전략.** Grace period 동시성과 탈취 탐지 분기는 단위 테스트가 아니라 실제 DB(테스트 컨테이너/H2)를 쓰는 통합 테스트로 검증한다 — `SELECT FOR UPDATE` 락은 mock으로 재현 불가능.

**REGRESSION (CRITICAL).** `OAuth2SuccessHandlerTest`(현재 통과 중, JSON body `{"token":"..."}` 검증)는 access+refresh를 쿠키로 응답하도록 바꾸면 깨진다. 구현과 동시에 이 테스트를 쿠키 기반 응답 검증으로 교체해야 한다.

**부수 발견 — 즉시 수정됨.** 리뷰 중 작업 디렉토리(커밋 안 된 변경)의 `SecurityConfig.kt:40`에서 `"/oauth2/**", "/login/oauth2/**"` 두 패턴이 `"/oauth2/**login/oauth2/**"` 하나의 잘못된 패턴으로 합쳐져 있는 걸 발견, 원래대로 두 패턴으로 복원했다. 이 버그를 방치했다면 `/login/oauth2/**` 콜백 경로가 permitAll에서 빠져 OAuth2 로그인 자체가 깨질 수 있었다.

## NOT in scope

- 계정 연동(linking) 시 refresh token 처리 정책 — 현재 Google 프로바이더만 사용 중이라 다중 프로바이더 연동 시나리오가 없음. 실제 연동 기능 작업 시 별도로 다룬다.

## What already exists

- `JwtService.parseUserId`가 이미 만료(`ExpiredJwtException`)/서명오류/파싱실패를 내부적으로 구분하는 catch 블록을 갖고 있음 — 재사용 가능, 재작성 불필요.
- `V1.4__create_users_identities.sql`이 단순 PK+FK+unique constraint 마이그레이션 패턴을 제공 — `refresh_tokens` 마이그레이션이 그대로 따라갈 수 있음.
- `AuthRestController`가 이미 `/me`로 존재 — 신규 컨트롤러 대신 여기에 메서드를 추가.

## API 계약: Access Token 만료 구분 (구현 필수 결정사항)

프론트는 "access token 만료라서 401"과 "애초에 유효하지 않은 토큰이라 401"을 구분할 수 있어야 한다. 구분이 안 되면 유효하지 않은 토큰에도 `/auth/refresh`를 반복 호출하는 무한 루프에 빠질 수 있다. `JwtAuthenticationFilter`가 만료(`ExpiredJwtException`)와 그 외 실패(서명 불일치, 파싱 실패)를 이미 내부적으로 구분하고 있으므로(`JwtService.parseUserId`), 이 구분을 401 응답에 실어 보낸다 — 예: `WWW-Authenticate: Bearer error="invalid_token", error_description="expired"` 헤더 또는 에러 응답 바디의 `code` 필드. 프론트는 `expired`일 때만 refresh를 시도하고, 그 외에는 즉시 재로그인으로 보낸다.

## 배포 마이그레이션

배포 시점에 기존 24h 단일 JWT를 들고 있는 사용자가 존재한다. 이 토큰들은 refresh 개념을 모르는 구 버전이므로, 별도 마이그레이션 없이 다음 정책을 취한다: 구 토큰은 새 `JwtAuthenticationFilter`에서도 access token과 동일하게 파싱되어(포맷이 같으므로) 만료 전까지는 정상 동작하고, 만료되면 refresh token이 없으므로 자동으로 재로그인하게 된다. 즉 배포 직후 최대 24시간 동안은 "구 토큰 사용자"와 "신규 access+refresh 사용자"가 공존하며, 별도 강제 로그아웃 조치는 side project 규모에서 불필요하다고 판단한다.

**주의 (whole-branch 리뷰 추가, 2026-09-04).** 위 "구 토큰이 계속 동작한다"는 보장은 `Authorization` 헤더로 토큰을 보내는 API 클라이언트에는 확실히 성립한다(`JwtAuthenticationFilter`가 헤더 경로를 그대로 지원). 다만 이 브랜치 이전에는 백엔드에 쿠키 관련 코드가 전혀 없었으므로, 브라우저/쿠키 클라이언트가 실제로 토큰을 어떻게 들고 있었는지는 프론트엔드 구현에 달려 있고 이 백엔드 변경이 통제할 수 있는 부분이 아니다 — 배포 전에 프론트엔드의 실제 토큰 저장 방식을 확인해야 한다.

## Success Criteria

- 재로그인 빈도가 현재보다 체감상 줄어듦 (refresh 덕분에 access 만료가 짧아도 세션 유지).
- 로그아웃 시 즉시 무효화됨 (해당 refresh token row 삭제로 확인 가능).
- 탈취된 refresh token 재사용 시도가 감지되고 대응(전체 세션 폐기 등)됨.
