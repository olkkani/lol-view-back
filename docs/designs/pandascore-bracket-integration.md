## Problem Statement

esports-api.lolesports.com's `getStandings` endpoint never populates `previousMatchIds` (verified live against Worlds 2025 and LCK 2026 Split 3 data — every match, including a double-elimination Regional Championship bracket, returned `previousMatchIds: []`). There is no way to reconstruct a winner's-bracket/loser's-bracket tree from it. The codebase's DB schema (`leagues`, `tournaments`, `matches`, `match_sets`) and its single `LolApiClientPort` → `LolEsportsApiClient` implementation both implicitly assume every `*_api_id` column is a lolesports.com ID — there is no provider/source concept anywhere.

PandaScore exposes a dedicated `GET /tournaments/{id}/brackets` endpoint whose `Match.previous_matches[]` field carries `{match_id, type: "winner"|"loser"}` — enough to reconstruct the bracket tree (though only in the backward direction; see Open Questions). The bracket visualization feature does not exist yet at all in this codebase.

## Status Quo

Bracket/standings visualization is not built. There is no fallback or degraded version today — the feature is entirely blocked on getting bracket-linkage data from somewhere other than lolesports.

## Constraints

- Solo-run project, `feature/standing` branch off `develop`.
- Existing lolesports sync pipeline (`PollMatchDataService`, `PollMatchSetService`, `TournamentSyncScheduler`, `MatchDailySyncScheduler`, `MatchSetSyncScheduler`) is in production and has a history of sync bugs (`fix: sync error match scheduler`, `fix: dedup existing matches/match_participants rows before adding UNIQUE constraints`). Treated as a no-touch zone for this work.
- `TournamentSyncScheduler` injects the concrete `LolEsportsApiClient` class directly, not the `LolApiClientPort` interface — an existing inconsistency, left as-is.

2. The actual goal this session is "ship the PandaScore bracket feature," not "complete a provider abstraction." **Agreed.**

They are complementary sources for different capabilities, not interchangeable ones. A shared interface may never be the right move, not just "not yet." ## Approaches Considered

### Approach A: Fully independent (recommended)
New `PandaScoreClient`, new `bracket_matches` table, new sync job, new read API — all standalone. `LolApiClientPort`, `leagues`, `tournaments`, `matches` untouched.
- Effort: S. Risk: Low.
- Pros: zero regression risk to the sensitive lolesports pipeline; PandaScore's response shape (`previous_matches[].type`, `structuralId`) can be modeled directly without forcing it into lolesports-shaped DTOs.
- Cons: lolesports tournament ↔ PandaScore tournament mapping needs a small manual lookup (no shared ID space); if a 3rd provider ever appears, today's two divergent patterns need reconciling then.

### Approach B: Narrow provider-branching interface
A new, bracket-only `BracketProviderPort` (not touching `LolApiClientPort`) with PandaScore as its sole implementation.
- Effort: M. Risk: Low-Medium.
- Rejected: with exactly one implementation and one call site, this is the "sample size of one" abstraction the cross-model review flagged — no polymorphism benefit realized today, and the interface shape can't be validated against reality until a second bracket-capable source exists.

### Approach C: Extend existing schema with a provider column
Add `data_source` to `leagues`/`tournaments`, extend `matches` with bracket-linkage columns.
- Effort: L. Risk: High.
- Rejected: forces changes into the no-touch lolesports sync/upsert logic (`MatchPollingDao`, `PollMatchDataService`) to make sure new columns don't break existing dedup/upsert behavior — directly violates the agreed no-touch constraint for zero benefit at current scale.

## Recommended Approach

**Approach A.** Matches the revised Premise 3: build exactly what the one real use case (bracket UI) needs, touch nothing that already works. The tournament-mapping gap (A's main con) is a small lookup table, not a design blocker.

## Real API Verification (2026-09-14, post-review)

The Assignment was completed against a live tournament (LCK 2026 Playoffs, `tournament_id=21722`). `GET https://api.pandascore.co/tournaments/{id}/brackets` returns a bare `Match[]` array (no `{data: ...}` wrapper). Confirmed against 9 real matches:

- `previous_matches[].type` is exactly `"winner"` / `"loser"` — no third value observed, including on the grand final (which had exactly one terminal match, two incoming `"winner"` links — no bracket-reset case in this data, so that outside-voice risk is neither confirmed nor ruled out by this sample).
- First-round matches correctly have `previous_matches: []` — no root-detection logic needed for the leaf case either; the edge-storage design (dropped tree-walk) is directly validated by this response shape.
- There is no `bracket_type`, `structuralId`, `round`, or `destinations` field anywhere in the response. Only `previous_matches[].type` (winner/loser) and the free-text `name` field (e.g. `"Upper bracket quarterfinal 1: T1 vs BFX"`, `"Grand final: GEN vs HLE"`) hint at bracket structure — neither is a clean enum.
- `opponents[]` holds full team objects (variable count — empty for a still-unpaired TBD slot, per PandaScore's docs on not-yet-determined matches). `results[]` holds `{team_id, score}`. `games[]` holds per-game detail (BO5 = up to 5 entries).
- Auth: PandaScore accepts both `?token=` query param and `Authorization: Bearer` header — decided to use the Bearer header (avoids the token appearing in URLs/access logs, and matches PandaScore's own documented recommendation), diverging from `LolEsportsApiClient`'s `x-api-key`-header convention only in header name, not in mechanism.
- Rate limit / plan tier: not yet hit a limit in ad-hoc testing; formal budget still unconfirmed — the 5-minute scheduler cadence ships as configurable and gets tuned once real usage surfaces a limit, rather than blocking further on this.

**Schema decisions made from this real data** (raw-storage over inferred/computed columns, decided in /superpowers:writing-plans):
- No `bracket_type` column — store `previous_matches` and `name` as raw JSON/text; infer bracket position at read time.
- No `team1_id`/`team2_id` columns — store `opponents` as raw `jsonb`, since the array is genuinely variable-length (TBD slots can have 0-1 populated).
- Tournament ID mapping: a new Flyway-backed `tournament_provider_mappings` lookup table (lolesports tournament ID ↔ PandaScore tournament ID), manually populated per active tournament — not a config file.

## /plan-eng-review Amendments (2026-09-14)

The eng review's outside-voice pass (Claude subagent, standing in for Codex which errored on `gpt-6-astra`) surfaced two changes to Approach A's shape, both accepted:

1. **API-first sequencing, not code-first.** The original plan committed to concrete architecture (5-min scheduler cadence, sequential tournament iteration, backward tree-walk algorithm) while 3 of the Open Questions below were entirely uninvestigated. The outside voice's point: rate-limit/API-shape unknowns aren't tuning knobs on this architecture — they can invalidate the DTO shape, the enum exhaustiveness, and the algorithm design itself. **Revised order: before any Flyway table, entity, or scheduler code is written, do a one-off script/CLI call against the real PandaScore API to resolve the Assignment's three verification items.** Only then design the DTOs, enum, and sync architecture.

2. **Store edges, don't walk a tree at sync time.** The original "walk backward from the root/final match" approach assumes exactly one terminal match per tournament. The outside voice flagged that a double-elimination grand-final bracket reset can produce two terminal matches, silently breaking any root-identification heuristic (last by date, highest round number, etc.). **Revised approach: the sync job stores every match and its `previous_matches` edges as-is (no root detection, no backward walk, no walk-failure state) — the bracket tree is assembled at read time by the query/API layer, not at sync time.** This also makes each match upsert independent and idempotent rather than tree-shaped.

These replace the tree-walk framing in the Cross-Model Perspective and Open Questions sections below; the "48-hour prototype" description there predates this revision.

## Open Questions

**Resolved by API-first sequencing (see Amendments above) — verify ALL of these against a real PandaScore response BEFORE writing any Flyway migration, entity, or scheduler code, via a one-off script/CLI call:**

- Whether `previous_matches[].type` ever emits values beyond `winner`/`loser` (e.g. a grand-final/decider marker) — the `bracket_type` enum's values depend on this; don't hardcode a 2-value enum until confirmed.
- PandaScore authentication/rate-limit plan (API key acquisition, plan tier, request budget per window) — this determines whether sequential-vs-parallel tournament iteration and the 5-min scheduler cadence are even viable, not just a tuning choice.
- The general shape/completeness of a real `GET /tournaments/{id}/brackets` response for at least one live or recently-completed tournament.

**No longer applicable (superseded by storing edges instead of walking a tree):**

- ~~What identifies the root/final match for a backward tree-walk~~ — moot: the sync job stores every match + its `previous_matches` edges as-is; no root detection or backward walk happens at sync time. (A double-elimination grand-final reset can produce two terminal matches, which would have silently broken any single-root heuristic — this is why the tree-walk approach was dropped, not just deferred.)

**Still open, decide during implementation (not blocking, not architecture-shaping):**

- PandaScore's bracket endpoint does include `not_started` matches with `previous_matches` already populated (confirmed via docs: "TBD vs TBD" matches are returned with their potential-participant linkage intact before either predecessor finishes) — so the sync job can and should ingest the empty bracket skeleton before results exist, not wait for completion.
- Lolesports tournament → PandaScore tournament ID mapping: mechanism not yet chosen (candidates: a small Flyway-managed lookup table keyed by both IDs, vs. a static config/YAML mapping). Given it's a handful of active tournaments at a time, either is cheap.
- **Log-spam guard for unmapped tournaments:** if most/all tournaments are unmapped on day one, skip-and-log must not fire every 5-minute tick per tournament forever — rate-limit the log itself (e.g. once per tournament per hour), not just the sync attempt.
- **Stale rows after PandaScore corrects a bracket** (e.g. an upset ruling reversed after the fact): since sync upserts by `(tournament_id, match_id)`, a corrected match naturally overwrites the stale row on the next sync tick with no separate handling needed — confirm this holds once real correction behavior is observed, since PandaScore's correction semantics (does it reuse the same `match_id`, or mint a new one?) are unverified.
- Sync job failure handling: skip-and-log per tournament (not abort-the-whole-job) is the default, since this is a new isolated pipeline with no shared state with lolesports sync.
- Re-sync/upsert semantics for `bracket_matches`: upsert by `(tournament_id, match_id)` — per-match idempotent now that sync stores edges rather than a tree, so this is simpler than originally scoped (no tree-shaped upsert ordering to worry about).
- Sync trigger: a new, independent `@Scheduled` job (not a manual endpoint) matching `MatchSetSyncScheduler`'s existing 5-minute cadence pattern, for real-time bracket data — cadence to be re-confirmed once rate limits are known (see API-first sequencing above).

## Success Criteria

- A `GET /tournaments/{id}/brackets`-style endpoint returns a tree-shaped response for at least one real PandaScore tournament, built without modifying any file under the existing lolesports sync path.
- The bracket skeleton renders (even with TBD/empty slots) before all matches in that tournament have finished.
- A second sync run against the same tournament updates `bracket_matches` in place (upsert by `(tournament_id, match_id)`, enforced as a DB-level UNIQUE constraint — not just an application-level convention) rather than duplicating or wholesale-replacing rows.
