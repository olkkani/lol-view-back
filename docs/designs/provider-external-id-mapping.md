# Design: Per-Entity Provider-ID Mapping (League/Tournament/Club)

Generated by /office-hours on 2026-09-20
Branch: feature/league
Repo: olkkani-lol-view-back
Status: APPROVED

## Problem Statement

The codebase currently has two divergent, incomplete patterns for storing provider-supplied external IDs:

- `leagues.league_api_id` and `tournaments.tournament_api_id` are single lolesports-only columns, baked directly into `League`/`Tournament` entities. `League.leagueApiId` is not just an identifier — it is passed as a direct argument into `LolApiClientPort` sync methods (`fetchTournaments(leagueApiId)`, `fetchMatches(leagueApiId)`) from `TournamentSyncScheduler` and `PollMatchDataService`.
- `TournamentProviderMapping` is a separate two-column lookup table (`lolesportsTournamentId`, `pandascoreTournamentId`) added for the bracket-stage integration, used only by `BracketSyncService` to translate a lolesports tournament ID into a PandaScore tournament ID before calling `PandaScoreClient.fetchBrackets`.
- `Club` has no provider-ID column at all today.

Now that PandaScore is being used to fill gaps lolesports can't cover for bracket stage tracking, league, tournament, and club rows all need PandaScore-side IDs alongside their lolesports IDs. Neither existing pattern generalizes: the column approach is single-provider and directly coupled to sync call sites; the lookup-table approach is bracket/tournament-specific and would need to be duplicated per entity per provider pair.

## Status Quo

Bracket-stage sync (`BracketSyncService`) works today via `TournamentProviderMapping`, a hand-populated two-ID lookup. Adding a third provider, or mapping League/Club, means either adding more single-purpose lookup tables (structurally repeating this same table three more times) or bolting more single-provider columns onto entities (repeating the `league_api_id` mistake).

## Constraints

- Solo-run project, `feature/league` branch off `develop`.
- Previous PandaScore integration (bracket stage) explicitly treated the lolesports sync pipeline (`TournamentSyncScheduler`, `PollMatchDataService`, `MatchDailySyncScheduler`, `MatchSetSyncScheduler`) as a no-touch zone due to its history of production sync bugs. **This constraint is explicitly lifted for this session** — the user confirmed sync call sites should be refactored this time, since `leagueApiId`/`tournamentApiId` being passed as raw strings into `LolApiClientPort` methods is exactly the coupling this design needs to remove. `MatchDailySyncScheduler` and `MatchSetSyncScheduler` are named here as part of the lifted constraint, but neither currently reads `leagueApiId`/`tournamentApiId` directly (confirmed by grep — only `TournamentSyncScheduler` and `PollMatchDataService` do); Success Criteria below covers exactly those two, not all four schedulers.
- `PandaScoreClient` remains bracket-only (`fetchBrackets`) in this pass — it does not gain implementations of `fetchMatchesForLeague`, `fetchMatchSet`, etc.

## Premises

1. The real problem is entity-to-provider-ID mapping, not a new fetch capability. **Agreed.**
2. `LolApiClientPort`'s method signatures are generalized this session (e.g. `leagueApiId: String` → a provider-aware id type — a small value class or data class pairing `Provider` and the raw string, not a bare `String`), but PandaScore does not get a full port implementation — `fetchBrackets` stays a standalone method. **Agreed.**
3. The existing `TournamentProviderMapping` table is retired and folded into the new generalized structure — no reason to keep two structurally identical mechanisms side by side. **Agreed.**

## Why this differs from the prior "one interface" rejection

The prior bracket-integration design doc rejected unifying `LolApiClientPort` and a PandaScore client behind one interface, calling it a "sample size of one" abstraction — PandaScore and lolesports are not two implementations of the same *capability* (lolesports has no bracket data; PandaScore's only value here is bracket data). That reasoning does not apply here: ID mapping is not a capability that only some providers implement, it is a structural property every provider has (every provider assigns its own opaque ID to the same real-world league/tournament/team). A live web check confirmed this is treated as a standard, well-known pattern in the industry ("external ID mapping" / "crosswalk table"), distinct in kind from unifying divergent capability interfaces.

## Approaches Considered

### Approach A: Per-entity provider-ID table, full generalization (recommended)
New tables `league_external_ids`, `tournament_external_ids`, `club_external_ids`, each shaped `(id, entity_id FK, provider varchar, external_id varchar)` with a UNIQUE constraint on `(entity_id, provider)`. `provider` follows the existing house convention for entity-level enums (see `LogoBackdrop` on `League` — a Kotlin enum persisted via `@Enumerated(EnumType.STRING)`), not a DB-level enum type. `League.leagueApiId` and `Tournament.tournamentApiId` columns are dropped, replaced by `provider = LOLESPORTS` rows. `TournamentProviderMapping` is retired — its two columns become two rows in `tournament_external_ids`. `LolApiClientPort` method signatures generalize (provider-aware id lookup replaces direct field access); `TournamentSyncScheduler` and `PollMatchDataService` are updated to resolve via a lookup instead of `.leagueApiId`, including the existing log statements in `TournamentSyncScheduler` that currently log `league.leagueApiId` directly (lines 37, 61-64, 68) — these resolve the lolesports ID through the new lookup the same way the sync calls do, not a separate mechanism. `fetchMatchDetail(matchApiId, leagueApiId)` is included in the signature generalization along with the other three `LolApiClientPort` methods.

**"Single lookup mechanism" resolved:** the three tables are each queried through a small `ExternalIdLookupService`, one method per entity type (e.g. `resolve(league: League, provider: Provider): String?`), backed by three JPA repositories. "Single lookup mechanism" in Success Criteria means one shared service class with a consistent method shape across entity types, not one shared table — the three-table decision in Schema Direction stands.

**Backfill migration, specified (revised — two migrations, not one, see CEO Review Amendments below):** Migration A adds the three new tables, then inserts one `LOLESPORTS`-provider row per existing `leagues.league_api_id` and `tournaments.tournament_api_id` value via `INSERT INTO ... SELECT id, 'LOLESPORTS', league_api_id FROM leagues WHERE league_api_id IS NOT NULL` (and the tournament equivalent) — using each entity's existing TSID `id` as the FK; no new IDs need to be minted for the mapping rows themselves beyond their own auto-generated TSID primary key. Existing `TournamentProviderMapping` rows backfill into `tournament_external_ids` the same way, one `LOLESPORTS` row and one `PANDASCORE` row per existing mapping. Migration A does **not** drop the old columns/table — application code (T1-T6, landing in the same deploy as Migration A) is already repointed onto the new tables and never reads the old columns, so they simply go unread from that deploy onward. Migration B (a small follow-up migration, run after a short production observation window) drops `league_api_id`/`tournament_api_id` and the `tournament_provider_mappings` table.
- Effort: M. Risk: Med (touches sync call sites; Migration A must run cleanly against production data — Migration B's later drop is low-stakes since nothing reads those columns by then).
- Pros: adding a future provider never needs a new table or column; one concept everywhere; collapses two structurally-duplicate existing patterns into one; splitting backfill from drop converts the migration's reversibility from "DB restore only" to "re-run Migration A is a no-op / defer Migration B" for the highest-risk step.
- Cons: every sync call site needs updating; two migrations to track instead of one (minor bookkeeping cost, not a risk).

### Approach B: Keep existing columns, add new tables only for what's missing
Rejected — leaves `league_api_id`/`tournament_api_id` as direct lolesports-only columns untouched, and adds separate provider-ID tables only for PandaScore. Ships faster and touches nothing sensitive, but leaves exactly the dual-mechanism inconsistency (direct column for lolesports, side-table for everyone else) the user wants removed. The next provider would still face a judgment call about which pattern to follow.

### Approach C: Full generalization + PandaScore as a complete port implementation
Rejected — out of scope for this session. Filling out `PandaScoreClient` to implement all of `LolApiClientPort` (not just brackets) mixes schema work with a much larger interface-implementation effort for no immediate payoff.

## Recommended Approach

**Approach A.** Matches the confirmed premises: the no-touch constraint is explicitly lifted this session, and the interface signature is meant to generalize. B is faster but reproduces the inconsistency this design exists to remove.

## Schema Direction (confirmed via landscape check)

A generic single polymorphic table (`entity_type` + `entity_id` + `provider` + `external_id`) was considered and rejected — it weakens foreign-key enforcement and risks orphaned rows when an entity type changes. Per-entity dedicated tables (mirroring the existing `TournamentProviderMapping` precedent) keep FK constraints explicit at the cost of one table per mapped entity type — an acceptable tradeoff at 3 entity types.

## Open Questions

- Exact `provider` enum values beyond `LOLESPORTS`/`PANDASCORE` — deferred until a third provider is actually integrated (YAGNI, consistent with the bracket design's "don't hardcode until confirmed" pattern).
- PandaScore league-level (not tournament/series-level) ID field name — not yet directly observed live; tournament/series (`id`) and team (`opponents[].opponent.id`) shapes were already confirmed live during the bracket integration work and are expected to follow the same numeric-ID convention per PandaScore's own API consistency. If The Assignment's live call reveals a non-numeric or composite League ID (e.g. a slug), `external_id varchar` already accommodates it without a schema change — only the assumption of "numeric-shaped" in prose would need updating, not the column type.
- **Unverified assumption (CEO review, outside voice):** the "no deploy-time risk window" finding and the "DB-restore-only rollback is acceptable" finding both rest on this project deploying as a single instance — asserted by the user, but no Dockerfile, CI/CD workflow, or deploy config exists anywhere in this repo to independently verify it. If this project ever moves to multi-instance/load-balanced deployment, both findings need to be re-checked: a rolling deploy could have an old-code instance still reading dropped columns while a new-code instance has already migrated the schema.

## /plan-eng-review Amendments (2026-09-21)

A Step 0 complexity check (8+ files, 4+ new classes) triggered a scope split, then an outside-voice pass (Claude subagent, standing in for Codex — `gpt-6-astra` not supported on this ChatGPT-auth Codex account, same issue noted in the bracket design doc) caught that the initial 3-phase split I proposed does not actually compile at its stated phase boundaries. Both are folded in here.

**Real scope is 2 atomic units, not 3.** The original doc's phase split (schema/backfill → interface generalization → sync call-site refactor) assumed the sync call-site refactor could land after and separately from the column drop. It cannot: `TournamentSyncScheduler` (`league.leagueApiId` at lines 37, 45, 61-64, 68), `PollMatchDataService` (`inProgressTournament.league.leagueApiId` at line 39), `LeagueRepository.findByLeagueApiId`, and — caught only by the outside-voice pass, not the first-pass review — `TournamentRepository.findByTournamentApiId` (load-bearing dedup-before-insert logic at `TournamentSyncScheduler.kt:47`, not just a log read) and `BracketSyncService.syncAllMappedTournaments()` (which calls `tournamentProviderMappingRepository.findAll()` — since `TournamentProviderMapping` is retired in the same migration, this call site must be repointed at the same time) all read the columns/table this migration removes. Between "schema PR merged" and "call-site refactor PR merged," the codebase does not compile. The real atomic unit is:

1. **Unit 1 (atomic, must land together):** new tables (`league_external_ids`, `tournament_external_ids`, `club_external_ids`, shared `@MappedSuperclass` base — see Approach A), the backfill-then-drop Flyway migration, `ExternalIdLookupService` (`resolve()` + batch `resolveAll()`), and **every** call site that reads the dropped columns or the retired table: `TournamentSyncScheduler`, `PollMatchDataService`, `LeagueRepository`/`TournamentRepository`'s derived-query methods, `TournamentPollingDao`'s jOOQ-based `toEntity()` mappers, `TournamentMapper`, `BracketSyncService`, and `db/seed/V9.2__seed-matchs.sql`.
2. **Unit 2 (separable):** `LolApiClientPort`'s method signature generalization (`leagueApiId: String` → provider-aware id type) plus `LolEsportsApiClient`'s implementation update. This is a pure interface change with no schema dependency — it can land before or after Unit 1.

**jOOQ is a second ORM path the original doc missed entirely.** `TournamentPollingDao.kt` reads `leagueApiId`/`tournamentApiId` via jOOQ-generated `LeaguesRecord`/`TournamentsRecord` (codegen driven by the live DB schema, `monosoul` Gradle plugin) — separate from the JPA `League`/`Tournament` entities. Dropping the columns regenerates those jOOQ records without the fields; `TournamentPollingDao`'s mappers must be updated in the same unit or the build breaks. `V9.2__seed-matchs.sql` inserts directly into `tournaments(tournament_api_id, ...)` and breaks the same way — this matches the already-logged `seed-data-hardcodes-user-ids-pre-auth` pitfall pattern for this repo (seed data silently drifts from schema changes unless updated in the same step).

**`ExternalIdLookupService` shape, finalized:**
- `resolve(entity, provider): String` — throws `MissingExternalIdException(entity, provider)` when no mapping row exists, rather than returning null. Callers (sync loops) catch this per-entity inside their existing try/catch (`TournamentSyncScheduler` already isolates failures per-league at lines 67-68) and skip+log, rather than crashing the whole scheduler run. `League.leagueApiId`/`Tournament.tournamentApiId` were non-null `String` before this migration — a silent nullable return would be a new, easy-to-miss failure mode.
- `resolveAll(entities, provider): Map<Long, String>` — a single `WHERE entity_id IN (:ids) AND provider = :provider` query (Spring Data derived query), not a loop over `resolve()`. Required because `TournamentSyncScheduler`/`PollMatchDataService` iterate collections of leagues/tournaments every poll cycle; without batching, the lookup reintroduces the N+1 that direct field access never had (previously free — an already-loaded entity field, now a query per iteration).
- Schema: `league_external_ids`/`tournament_external_ids`/`club_external_ids` share a `@MappedSuperclass` base entity (`id`, `provider`, `externalId`) — each concrete entity adds only its own FK column. Repositories extend a shared `JpaRepository<T, Long>` pattern with a common `findByEntityIdAndProvider` derived-query method name. Keeps the 3 tables' inevitable duplication (same 4 columns, same `UNIQUE(entity_id, provider)` constraint) to a consistent pattern rather than 3 fully independent copies.

**Rollback risk, resolved in CEO review (see Amendments below):** the original backfill-then-drop single-migration design had no rollback boundary short of a DB restore. Splitting into Migration A (backfill only) and Migration B (drop, deferred) fixes this — see CEO Review Amendments.

## /plan-ceo-review Amendments (2026-09-21)

An 11-section HOLD SCOPE review (no scope expansion — this is backend refactor work, already tightly bounded by the eng review) surfaced 6 findings across Architecture, Error/Rescue Map, and Observability, all resolved. A second outside-voice pass (Claude subagent, Codex again unavailable on this account) then caught something both prior review passes missed: **the design conflated code-level atomicity with SQL-migration-file atomicity.**

**Migration split (the load-bearing finding).** Unit 1 needing every call site repointed in the same deploy (a real, correctly-derived constraint — see eng-review Amendments) does NOT require the backfill and the column/table drop to live in the *same Flyway migration file*. Application code only needs the drop to have happened by the time it stops reading the old columns — which is true the moment Unit 1's code deploys, since that code never reads `league_api_id`/`tournament_api_id`/`tournament_provider_mappings` again. So:
- **Migration A** (ships with Unit 1): creates the three new tables, backfills them (`WHERE ... IS NOT NULL` filter, per the eng-review NULL decision), does **not** touch the old columns/table.
- **Migration B** (a follow-up, run after a short production observation window once Migration A's backfill is confirmed correct): drops `league_api_id`, `tournament_api_id`, and `tournament_provider_mappings`.

This converts the single highest-risk step in the whole design — previously "DB restore is the only rollback" — into "Migration A failing is a no-op retry; Migration B is a low-stakes follow-up deploy, not bundled with the risky part." Reversibility improves without loosening Unit 1's code-atomicity requirement at all.

**Other CEO-review findings, resolved:**
- **Rollback posture (architecture):** DB-restore-only rollback for Migration A itself (post-split, this is now just the backfill) is accepted for this solo-run project, backstopped by a pre-deploy manual verification step (below) rather than an automated rollback lever.
- **`BracketSyncService` needs a new filtered query, not raw iteration (error/rescue map):** today `TournamentProviderMapping.findAll()` only returns tournaments that already have *both* a lolesports and a PandaScore mapping (guaranteed by the table's 2-column shape). Post-migration, `BracketSyncService` needs an explicit `findTournamentIdsWithBothProviders(LOLESPORTS, PANDASCORE)` repository query (an `INNER JOIN` of `tournament_external_ids` to itself on `entity_id` for both provider values) to preserve that same filtering — otherwise every tournament with a lolesports mapping but no PandaScore mapping yet (the common case) would throw `MissingExternalIdException` on every 5-minute tick.
- **Concurrent-insert race:** confirmed not a real risk — no application codepath in this design's scope inserts new mapping rows during runtime (backfill is a one-time deploy-time operation; new-entity creation + mapping is out of scope, deferred to future work).
- **Security:** no new HTTP endpoints, no new user input paths, no new secrets — confirmed no new attack surface.
- **Migration auditability:** `RAISE NOTICE` in the migration SQL was rejected (outside voice caught this — it only reaches the ephemeral deploy log stream, not anything durable, so it doesn't actually satisfy the "verify 3 weeks later" goal it was proposed for). Instead, Migration A writes its before/after row counts into a real, durable table (persists in the DB alongside the already-durable `flyway_schema_history`, confirmed present via `includeFlywayTable.set(true)` in `build.gradle.kts`).
- **Log level:** `MissingExternalIdException` logs at `log.warn` (a data-not-yet-mapped state, not a system failure) rather than `log.error` (reserved for actual API/system failures) in every catch site — including `BracketSyncService.logFailureRateLimited`, which the outside voice caught was missing from T3's original file list (added).
- **Deploy-time risk window:** confirmed this project deploys as a single instance (Flyway auto-runs migrations at boot, single-instance restart is atomic from a schema-consistency perspective) — no old-code/new-code-see-different-schema window exists. Note: this is an **unverified assumption** — the outside voice confirmed no Dockerfile, CI/CD workflow, or deploy config exists anywhere in this repo to check it against; it rests entirely on the user's statement. Both this finding and the accepted DB-restore-only rollback for Migration A lean on the same unverified single-instance assumption.
- **Reversibility, revised: 3/5** (up from the original 2/5 assessment, reflecting the migration split — Migration A is now a low-stakes, re-runnable-as-a-no-op step; only Migration B, deferred until Migration A is observed-correct, carries irreversible risk, and by then the blast radius of a bad Migration B is much smaller).

## Success Criteria

- `League`, `Tournament`, and `Club` can each hold a lolesports ID and a PandaScore ID simultaneously, retrievable via a single lookup mechanism shared across all three entity types.
- `TournamentProviderMapping` is removed; `BracketSyncService` reads from the new generalized structure instead.
- `TournamentSyncScheduler` and `PollMatchDataService` resolve the lolesports ID through the new lookup rather than direct field access on `League`/`Tournament`.
- Adding a third provider requires no new table and no entity schema change — only new rows.

## Dependencies

- None external. Builds on the existing PandaScore integration (`PandaScoreClient`, `PandaScoreProperties`) from the bracket-stage work on `feature/standing`.

## NOT in scope

- **PandaScore as a full `LolApiClientPort` implementation** (`fetchMatchesForLeague`, `fetchMatchSet`, etc.) — deferred; `PandaScoreClient` stays bracket-only. No immediate payoff for the added surface area (rejected as Approach C).
- **`provider` enum values beyond `LOLESPORTS`/`PANDASCORE`** — deferred until a third provider is actually integrated. Hardcoding values for a hypothetical provider is YAGNI.
- **A shared polymorphic `external_ids` table** (single table, `entity_type` discriminator) — considered and rejected in favor of per-entity tables; weaker FK enforcement, orphan-row risk on entity-type changes.
- **Automated rollback for Migration A** (post-split, this is now just the backfill) — no automated rollback lever exists short of a DB restore; the pre-deploy manual verification step and Migration A's inherent re-runnability (no destructive drop) are the accepted mitigation for this solo-run project.
- **New leagues/tournaments/clubs creation with mapping insertion** — this design covers mapping *existing* entities to providers; the flow for creating a brand-new entity and inserting its first provider mapping is explicitly out of scope, deferred to future work (confirmed no concurrent-insert race exists today because this flow doesn't exist yet).
- **Multi-instance deployment safety** — this design's deploy-order conclusions (no risk window, DB-restore-only rollback acceptable) assume single-instance deployment, asserted by the user but unverified against any deploy config in this repo (none exists). If the project ever moves to multi-instance/load-balanced deployment, this needs re-verification.

## Dream state delta

The 12-month ideal (from Step 0C): any entity (League/Tournament/Club/future entity) gets a new provider mapped by inserting rows — zero schema change, zero new table, ever again. This plan is not a step toward that ideal; it **is** that ideal, fully realized for the three entity types that exist today. The only gap between "this plan, shipped" and "the ideal" is Unit 2 (LolApiClientPort's remaining single-provider-shaped signature) and PandaScore's own port implementation (explicitly deferred, not a gap in this design — a genuinely separate future decision). Nothing in this plan moves away from the ideal or creates a detour; it is the direct, complete path to it for the ID-mapping problem specifically.

## What already exists

- `TournamentProviderMapping` (entity + repository) — the direct precedent for this design's per-entity mapping-table pattern, currently used only by `BracketSyncService` for lolesports↔PandaScore tournament ID translation. Retired and folded into `tournament_external_ids` rather than reused as-is, since its 2-provider-only shape doesn't generalize to N providers or to League/Club.
- `TournamentProviderMappingRepositoryTest.kt` (`@DataJpaTest` + Testcontainers Postgres) — the existing test pattern the new `LeagueExternalIdRepositoryTest`/`TournamentExternalIdRepositoryTest`/`ClubExternalIdRepositoryTest` should follow directly; no new test infrastructure needed.
- `TournamentSyncScheduler`'s existing per-league `try`/`catch` (lines 67-68) — reused as the error-isolation boundary for `MissingExternalIdException`, rather than building new failure-handling infrastructure.
- `LogoBackdrop` enum convention (`@Enumerated(EnumType.STRING)`, top-level class in the `entity` package) — reused directly for the new `Provider` enum rather than introducing a different persistence convention.
