## Problem Statement
`user_followed_clubs`, `user_followed_leagues` 테이블은 이미 존재하지만 `users` 테이블은 `id` 컬럼 하나뿐인 빈 스켈레톤이고, 실제 인증 로직은 아무것도 구현돼 있지 않다. 사용자가 클럽을 팔로우하는 개인화 기능을 쓰려면 "이 사람이 누구인가"를 판별할 방법이 필요하다.

비밀번호를 직접 관리하는 책임(해싱, 유출, 재설정 플로우)을 지고 싶지 않아 처음부터 소셜 로그인만 고려했다. 로그인 제공자 후보는 Google/Discord/Telegram 세 개이며 아직 확정되지 않았다. 핵심 요구사항은 "한 사람이 여러 제공자로 로그인해도 팔로우 클럽 목록 같은 데이터가 하나의 계정으로 이어져야 한다"는 것 — 즉 단순 "로그인 성공 → JWT 발급"이 아니라 프로바이더 간 계정 연동(account linking)까지 포함하는 문제다.

## What Makes This Cool
어느 소셜로 로그인하든 같은 사람이면 같은 팔로우 목록을 보게 되는 것 자체가 "내 계정"이라는 감각을 만든다. 그리고 Telegram 연동을 어차피 구현하면, 팔로우한 클럽의 경기 알림을 Telegram 봇으로 푸시하는 확장이 거의 공짜로 따라온다 — 인증 배관이 알림 기능의 절반을 먼저 깔아두는 셈이다.

## Constraints
- `users` 테이블은 현재 `id` 컬럼만 있어 마이그레이션 부채 없이 자유롭게 설계 가능
- `build.gradle.kts`에 `spring-boot-starter-security-oauth2-client`, `spring-boot-starter-security`가 주석 처리돼 있고, `gradle/libs.versions.toml`에는 `jjwt`(io.jsonwebtoken)가 이미 정의돼 있음 — 의존성 추가 자체는 주석만 풀면 됨. 다만 이 항목들은 batch/data-rest/hateoas 등 프로젝트와 무관한 다른 보일러플레이트와 함께 일괄 주석 처리된 흔적이라, "이 조합이 이미 검토됐다"는 확정 신호로 보지는 않는다.
- Telegram은 표준 OAuth2가 아니다 — Telegram Login Widget이 자체 서명(HMAC-SHA256, bot token 기반)한 payload를 검증하는 별도 경로가 필요하다. Spring Security의 OAuth2 client 추상화에 태울 수 없다.
- 프론트엔드가 아직 없다 — 백엔드가 완결된 API 계약을 먼저 제공하고 프론트는 나중에 그 계약에 맞춰 붙는다.
- 사이드 프로젝트 규모(개인 학습 목적)이므로 리프레시 토큰, 계정 연동 해제 UI 같은 부가 기능은 초기 스코프에서 제외해도 됨.
- JWT 만료는 24시간, 리프레시 토큰 없음 — 만료 전 로그아웃/즉시 무효화(revocation) 수단이 없다는 뜻이다. 유출된 JWT는 최대 24시간 동안 유효하다. 사이드 프로젝트 규모에서는 받아들이는 트레이드오프로 명시하고, 문제가 되면(예: 실제로 토큰 유출 사고) 그때 denylist 등을 검토한다.

## Premises
1. 이메일/비밀번호 직접 관리는 하지 않는다 — 소셜 로그인만 지원한다. — **동의**
2. 로그인 제공자는 Google/Discord/Telegram 중 여러 개가 될 수 있으며, 최종 조합은 아직 미확정이다. — **동의**
3. `users`(계정 자체)와 `user_identities`(provider + provider_user_id, 계정에 연결된 개별 소셜 신원)를 분리한 테이블로 설계한다 — 한 유저가 여러 프로바이더를 가질 수 있어야 하기 때문. — **동의**
4. 계정 연동은 로그인된 상태에서 사용자가 명시적으로 "계정 연결하기" 액션을 수행할 때만 이루어진다. 이메일 일치 등으로 자동 병합하지 않는다 — 자동 병합은 이메일 스푸핑이 가능한 프로바이더가 하나라도 있으면 계정 탈취 벡터가 되기 때문. — **동의**
5. 세션 유지 방식(JWT vs 쿠키)은 프로바이더/연동 모델과 독립적인 별개의 결정이다. — **동의**
6. (세컨오피니언 반영) OAuth2 표준 경로(Google/Discord)와 Telegram의 비표준 HMAC 검증 경로는 반드시 단일한 `resolveIdentity(provider, providerUserId, currentSessionUserId?)` 함수로 수렴해야 한다. 두 경로가 각자 다른 분기 로직으로 구현되면, "이 provider_user_id가 이미 로그인된 세션에 연결을 시도하는 것인가"라는 체크가 한쪽에서 누락될 수 있고 이것이 곧 계정 탈취 구멍이 된다. — **동의, 필수 제약으로 반영**
7. (리뷰 반영) `provider_user_id`가 이미 **다른** `user_id`에 연결돼 있는데 또 다른 계정이 그 프로바이더로 연동을 시도하면(충돌 케이스), 자동으로 아무 계정에나 붙이지 않고 명시적으로 거부한다(409). 이건 Premise 4/6이 막으려는 계정 탈취 시나리오와 정확히 같은 종류의 위험이므로 `resolveIdentity`의 정식 분기로 다룬다. — **동의, `resolveIdentity` 계약에 반영**

## Cross-Model Perspective
Codex CLI는 인증 만료(401)로 실행하지 못해, 독립적인 Claude subagent로 세컨오피니언을 받았다 (프롬프트만 보고 이 대화 맥락은 보지 못한 상태에서 콜드 리드).

- **가장 흥분한 지점 지적**: "팔로우 클럽 목록과 같은 정보들이 서로 연동되었으면 좋겠어"라는 표현을 짚으며, 실제 관심사는 인증 자체가 아니라 팔로우 목록이라는 지속 자산이라고 지적 — 프로바이더 3개를 한 번에 다 붙이려 하지 말고 Google 하나를 팔로우 API까지 끝까지 완결한 뒤 확장하라는 스코프 조언으로 이어짐.
- **기존 도구 활용**: `spring-boot-starter-oauth2-client`가 Google/Discord의 authorization-code flow, state/PKCE/CSRF 처리를 대부분 해결해준다는 점을 재확인. 직접 짜야 하는 50%는 `user_identities` 테이블 + 연동 로직, JWT 발급, Telegram 전체(라이브러리 없음, HMAC-SHA256 직접 구현 ~40줄).
- **핵심 보안 리스크(가장 중요한 반영 사항)**: OAuth2와 Telegram HMAC 검증 각각은 안전한 경로이지만, 두 경로가 서로 다른 코드 분기로 구현되면 이음매에서 계정 탈취 구멍이 생긴다. 이 지적을 Premise 6으로 승격해 필수 제약에 반영했다.
- **재밌는 미고려 방향**: 연동된 신원을 모아 보여주는 공개 프로필 페이지(`/u/{handle}`), 그리고 Telegram HMAC 검증을 이미 구현하는 김에 Telegram 봇을 팔로우 클럽 알림 채널로 확장하는 아이디어. 둘 다 이번 스코프 밖(Open Questions 참고).

## Approaches Considered

### Approach A: OAuth2 Client + 자체 JWT 발급 (선택됨)
Summary: `spring-boot-starter-oauth2-client`로 Google/Discord의 표준 OAuth2 흐름을 처리하고, Telegram은 HMAC-SHA256 서명 검증을 직접 구현한다. 두 경로 모두 identity 확인 후 `user_identities`를 조회/생성하고, 백엔드가 서명한 JWT를 발급해 프론트에 내려준다.
Effort: M (human: ~2-3일 / CC: ~2-3시간)
Risk: Low
Pros:
- 이미 `libs.versions.toml`에 필요한 의존성(`spring-security`, `spring-oauth2`, `jjwt`)이 정의돼 있어 추가 작업이 적음
- 프론트가 세션 쿠키가 아닌 순수 JWT만 다루면 되므로 "백엔드 먼저, 프론트 나중" 순서와 맞음 — 어떤 프론트(웹/모바일)가 붙어도 API 계약이 동일
Cons:
- Telegram이 표준 OAuth2가 아니라 별도 검증 경로가 필요하고, 이 경로를 OAuth2 경로와 다르게 구현하면 계정 탈취 위험(Premise 6)이 생김 — 단일 `resolveIdentity` 함수로 강제 수렴시켜야 함
Reuses: `libs.versions.toml`의 `spring-security`/`spring-oauth2`/`jjwt` 번들, 기존 `users`/`user_followed_clubs` 테이블

### Approach B: OAuth2 Client + Spring Session(쿠키, JWT 없음)
Summary: 로그인 처리는 A와 동일하되, JWT 대신 Spring Security 기본 세션(서버 메모리/Redis + 브라우저 세션 쿠키)으로 상태를 유지한다.
Effort: S (human: ~1-2일 / CC: ~1-2시간)
Risk: Low
Pros:
- 로그아웃 시 서버에서 즉시 세션 무효화 가능 (JWT는 만료 전 자체 무효화가 안 됨)
- 서명 키 관리, 만료 로직을 직접 짤 필요가 없어 구현이 더 단순
Cons:
- 프론트가 나중에 모바일 등으로 확장되면 쿠키 기반은 크로스 도메인/네이티브 앱에서 다루기 번거로움 — "백엔드 먼저, 프론트 나중" 계획과 방향이 덜 맞음
- **거부됨**: JWT의 단순한 멀티클라이언트 계약을 우선시해 트레이드오프를 받아들이기로 결정

### Approach C: 프로바이더별 자체 검증 (Spring Security OAuth2 미사용)
Summary: Spring Security의 OAuth2 클라이언트를 쓰지 않고, 각 프로바이더 API를 직접 호출해(Google tokeninfo, Discord `/users/@me`, Telegram 위젯 서명) 통일된 커스텀 컨트롤러로 신원을 검증한다.
Effort: M-L (human: ~3-4일 / CC: ~3-4시간)
Risk: Med
Pros:
- 세 프로바이더가 어차피 제각각 표준이 달라(Telegram은 OAuth2가 아님), 처음부터 하나의 통일된 인터페이스로 직접 짜면 나중에 "표준 vs 예외" 이질감이 안 생김
Cons:
- Google/Discord 검증 로직(서명 검증, state/CSRF 처리)을 직접 짜야 해서 버그 위험이 A보다 큼 — 보안 책임을 최소화하려는 원래 목표와 정면으로 충돌
- **거부됨**: 표준 라이브러리가 제공하는 검증된 경로를 포기할 이유가 없음

## Recommended Approach
**Approach A** — Google/Discord는 `spring-boot-starter-oauth2-client`로 검증된 경로를 그대로 쓰고, Telegram만 별도 HMAC 검증을 추가한다. 단, Premise 6에 따라 OAuth2 콜백과 Telegram 검증 두 경로 모두 `resolveIdentity(provider, providerUserId, currentSessionUserId?)` 단일 함수를 통과하도록 강제한다 — 이 함수가 "이미 로그인된 세션에 연결을 시도하는 것인지" 여부를 판단해 명시적 연동(Premise 4)과 신규 로그인을 분기한다.

### `resolveIdentity` 계약 (리뷰 반영 — 반드시 코드 작성 전 확정)
```
fun resolveIdentity(
    provider: Provider,
    providerUserId: String,
    currentSessionUserId: Long?,   // JWT가 있으면 그 user_id, 없으면 null
): ResolveResult

sealed class ResolveResult {
    data class LoggedIn(val userId: Long)        // 기존 identity로 로그인 성공
    data class NewUser(val userId: Long)          // 신규 identity → 신규 user 생성
    data class Linked(val userId: Long)            // currentSessionUserId에 새 identity 연결 성공
    object AlreadyLinkedElsewhere : ResolveResult() // 이 provider_user_id가 다른 user에 이미 연결됨 → 409
}
```
- `currentSessionUserId == null`이고 identity가 이미 있음 → `LoggedIn`
- `currentSessionUserId == null`이고 identity가 없음 → `NewUser`
- `currentSessionUserId != null`이고 identity가 없음 → 그 user에 연결 → `Linked`
- `currentSessionUserId != null`이고 identity가 있는데 `user_id`가 다름 → `AlreadyLinkedElsewhere` (거부, 자동 병합 금지)
- `currentSessionUserId != null`이고 identity가 있고 같은 `user_id`(재로그인) → `LoggedIn`

### 통합 지점 (리뷰 반영 — 숨겨진 복잡도)
Spring Security의 OAuth2 로그인(Google/Discord)은 필터 체인 안에서 `Authentication`을 만들어내는 리다이렉트 기반 흐름이고, Telegram은 평범한 `@PostMapping` REST 컨트롤러다. 두 흐름의 요청/응답 생명주기가 다르므로 "함수 하나만 만들면 끝"이 아니라, 다음 두 지점에서 각각 `resolveIdentity`를 호출하도록 명시적으로 연결해야 한다:
- OAuth2 경로: 커스텀 `AuthenticationSuccessHandler`를 등록해 그 안에서 `resolveIdentity` 호출 (Spring Security 기본 핸들러를 그대로 쓰지 않음)
- Telegram 경로: 컨트롤러가 HMAC 검증에 성공한 직후 동일한 `resolveIdentity` 호출

### 계정 연결 시 기존 로그인 상태를 어떻게 전달하는가 (리뷰 반영)
"로그인된 상태에서 계정 연결하기"를 누르면 Discord/Google의 OAuth2 인가 흐름은 브라우저 리다이렉트를 거치므로, 이 요청에 기존 JWT를 실어 보낼 표준 헤더(`Authorization`)를 쓸 수 없다. OAuth2 `state` 파라미터에 현재 로그인된 `user_id`(또는 그 대체용 일회성 링크 토큰)를 담아 콜백에서 다시 꺼내 `currentSessionUserId`로 넘긴다. Telegram은 리다이렉트가 없는 일반 REST 호출이므로 `Authorization` 헤더로 그대로 전달하면 된다.

**이 설계에서 가장 리스크가 큰 미확정 구현 지점(리뷰 재확인).** `state` 파라미터는 원래 Spring Security OAuth2 client 내부가 CSRF/재생공격 방지 용도로 직접 소유·왕복시키는 값이라, 여기에 우리 애플리케이션 데이터(`currentSessionUserId`)를 얹으려면 (a) `OAuth2AuthorizationRequestResolver`를 확장하거나 (b) nonce로 서버 측 캐시를 조회하는 사이드 채널 중 하나를 택해야 한다 — 둘 다 간단한 설정 변경이 아니라 별도 구현이 필요하다. Next Steps 3의 하위 작업으로 명시한다.

## Open Questions
- Telegram 봇을 알림 채널로 확장하는 것(세컨오피니언 제안) — 이번 인증 스코프 밖, 팔로우 클럽 API가 실제로 동작한 뒤 별도 세션에서 검토.
- 공개 프로필 페이지(`/u/{handle}`) — 이번 스코프 밖, 아이디어로만 기록.
- 리프레시 토큰 전략 — 사이드 프로젝트 규모에서는 짧은 JWT 만료 + 재로그인으로 충분하다고 잠정 결정했으나, 실제 사용 중 불편하면 재검토.
- 계정 연동 해제(unlink) UI/API — 초기 스코프 제외.
- 최종 프로바이더 조합(Google/Discord/Telegram 셋 다 vs 일부) — Next Steps에서 Google부터 먼저 완결하는 순서로 자연히 좁혀질 예정. `user_identities` 테이블 자체는 `provider` 컬럼이 문자열/enum이라 세 개를 한 번에 설계해도 추가 비용이 없지만, Discord/Telegram의 실제 등록·컨트롤러 구현(Next Steps 6, 8)은 Google이 끝까지 동작한 뒤 순서대로 진행한다 — 세컨오피니언의 "Google 먼저 완결" 조언은 스키마가 아니라 구현 순서에 적용한다.

## Success Criteria
- Google로 로그인하면 `user_identities`에 신규 identity가 생성되고 JWT가 발급된다. JWT 만료는 기본 24시간으로 한다 (리프레시 토큰 없음, 만료 후 재로그인 — Open Questions 참고).
- 로그인된 상태에서 Discord "계정 연결하기"를 실행하면 같은 `user_id`에 두 번째 identity가 추가된다 (자동 병합이 아닌 명시적 액션으로만, `resolveIdentity`의 `Linked` 결과).
- 이미 다른 계정에 연결된 `provider_user_id`로 연동을 시도하면 409로 거부된다 (`AlreadyLinkedElsewhere`) — 자동 병합되지 않는다.
- 로그인 없이 팔로우 클럽 API를 호출하면 401이 반환된다.
- 만료되었거나 서명이 잘못된 JWT로 요청하면 401이 반환된다 (검증 필터가 이 케이스를 다룬다).
- 로그인 후 팔로우 클럽 API가 실제 `user_id`를 사용해 동작한다 (현재 스텁 상태에서 벗어남).
- `GET /me`가 로그인된 사용자의 `user_id`와 연결된 identity 목록(provider별)을 반환한다. 각 identity의 표시 정보(이메일/닉네임/아바타 등)를 얼마나 담을지는 프로바이더 응답 스키마 확인 후 구현 시점에 정한다 (Next Steps 4에서 Google 응답을 실제로 받아본 뒤 확정 — 지금은 최소 `provider` + `provider_user_id`만 보장).
- Telegram 컨트롤러도 OAuth2 콜백과 동일하게 `resolveIdentity`가 `AlreadyLinkedElsewhere`를 반환하면 409를 응답한다 (별도 REST 컨트롤러이므로 이 매핑을 Telegram 쪽에도 명시적으로 구현해야 한다 — 필터 체인이 대신 처리해주지 않음).
- OAuth2 콜백 경로와 Telegram HMAC 경로가 동일한 `resolveIdentity` 함수를 거친다는 것이 코드 리뷰로 확인 가능하다.

## Next Steps

**이번 엔지니어링 리뷰 범위는 1-5(Google 전용 1차 구현)로 한정한다.** 6-8(Discord/Telegram/link 엔드포인트)은 1-5가 실제 코드로 존재한 뒤 별도 리뷰로 진행한다 — Step 0 스코프 챌린지에서 사용자와 합의된 결정이며, 이후 재논의하지 않는다.

2. `build.gradle.kts`에서 `spring-boot-starter-security-oauth2-client` 관련 라인 주석 해제, `jjwt` 의존성 활성화. (`spring-boot-starter-security` 자체는 이미 활성 의존성이다 — 신규가 아니라 확인용.) `application.yaml`에 누락된 `on-profile: security` 블록을 신설하고 여기에 Google OAuth2 client-id/secret 등록을 추가한다 — profile group(`dev`/`prod`)이 이미 `security`를 참조하고 있지만 실제 블록이 파일 어디에도 없다.
3. `resolveIdentity(provider, providerUserId, currentSessionUserId?)` 함수 설계 및 구현 (계약은 Recommended Approach 참고, `domain/auth/ResolveIdentityService.kt`) — 이번 설계의 핵심 안전장치이므로 다른 어떤 컨트롤러보다 먼저 작성하고 단위 테스트로 고정한다. Google의 `providerUserId`는 OIDC `sub` 클레임을 사용한다 — 이메일은 계정 설정에 따라 안 올 수 있어 식별자로 부적합하다. 최소 테스트 케이스: (a) 신규 로그인, (b) 재로그인, (c) 명시적 연동 성공, (d) 연동 시도인데 이미 다른 유저에 연결됨(409), (e) OAuth2 콜백과 Telegram 컨트롤러 양쪽에서 동일 함수가 호출되는지. 이 단계에서 `currentSessionUserId`를 OAuth2 리다이렉트에 실어 보내는 서명된 `state` 토큰(또는 nonce 기반 서버 캐시) 설계도 함께 확정한다 — Recommended Approach에서 짚었듯 이 설계 전체에서 가장 구현이 불확실한 지점이다.
3.5. **[신규 — 리뷰에서 추가]** JWT 검증 필터 구현 (`infastructure/inbound/web/security/JwtAuthenticationFilter.kt`) — `Authorization: Bearer <jwt>` 헤더 파싱, 서명/만료 검증 실패 시 401, 유효하면 `SecurityContext`에 `user_id` 주입. 기존 `infastructure/config/SecurityConfig.kt`(현재 `anyRequest().permitAll()`로 전체 열려 있음)를 수정한다: `/oauth2/**`, `/login/oauth2/**`는 permitAll 유지(Google 로그인/콜백 경로), `/clubs` 등 인증이 필요한 엔드포인트는 `authenticated()`로 전환, JWT 필터를 `UsernamePasswordAuthenticationFilter` 앞에 추가. CSRF는 쿠키 기반 상태가 아니므로 비활성 유지 가능. Google 동의 화면에서 사용자가 거부하면(콜백에 `error=access_denied` 등 파라미터로 도착) `resolveIdentity`를 호출하지 않고 400을 반환한다.
4. Google OAuth2 연동 (신설한 `on-profile: security` 블록에 `spring.security.oauth2.client.registration.google.*` 추가) → 성공 시 커스텀 `AuthenticationSuccessHandler`가 `resolveIdentity` 호출 → JWT 발급 → `GET /me` 엔드포인트로 확인

## Failure modes
| 코드패스 | 실패 시나리오 | 테스트 커버 | 에러 핸들링 | 사용자 경험 |
|---|---|---|---|---|
| `resolveIdentity` 신규/재로그인 분기 | 없음(순수 함수) | GAP (구현 전) | N/A | N/A |
| `resolveIdentity` 충돌 분기 | 동시에 같은 provider_user_id로 두 요청 도착 (race) | GAP | unique 제약 위반 시 `DataIntegrityViolationException` → 409 매핑 필요 | 명확한 409, 조용한 실패 아님 (매핑 구현 시) |
| OAuth2 콜백 | Google이 `error=access_denied`로 도착 | GAP (Next Steps 3.5로 추가) | resolveIdentity 호출 안 하고 400 | 명확한 4xx |
| JWT 검증 필터 | 만료/서명 불일치 토큰 | GAP | 401 반환 | 명확한 401 |
| `GET /clubs` | JWT 없이 호출 | GAP | 401 (SecurityConfig `authenticated()`) | 명확한 401 |

**Critical gap:** `resolveIdentity`의 충돌 분기(같은 `provider_user_id`로 동시 요청)에 대한 테스트도 에러 핸들링도 아직 구현되지 않았다 — DB의 `unique` 제약이 최후 방어선이지만, 그 예외를 409로 매핑하는 코드가 없으면 500이 사용자에게 노출된다. Next Steps 3의 테스트 케이스 (d)가 이걸 다루지만, `DataIntegrityViolationException` 핸들링을 명시적으로 추가해야 한다.
